## 2. 产品定位与目标

### 2.1 产品定位

面向单个住宅社区，提供物业管理与普通业主自助服务的一体化 Web 平台。两套前端界面使用同一后端和业务数据库，通过明确的身份与数据权限互通，避免将业主端做成隐藏几个菜单的管理后台。

当前运行于浏览器，不是独立桌面软件、原生 App 或微信小程序。前后端分离不等于已部署微服务；当前主要可运行后端是 `smart-community-admin`。

### 2.2 核心问题

1. 物业档案、服务工单、账务和居民互动分散，缺少对象关联及一致状态。
2. 普通业主需要独立入口，并且只能查看本人业务数据。
3. 管理端覆盖面较广，但部分模块仍停留在记录管理、演示或局部闭环。
4. 智能问答需要可配置的云端模型，并与用户权限隔离，不能成为越权查询入口。
5. 页面需要统一导航、表单、详情、错误反馈与统计口径，不能仅完成视觉美化。

### 2.3 产品目标

| 目标 | 判断方式 | 当前结论 |
| --- | --- | --- |
| 双端边界清晰 | 普通业主无法访问管理接口及他人私有对象 | 已有服务端隔离与测试，仍需持续回归 |
| 服务两端互通 | 业主提交的工单在管理端处理，结果回到同一业主 | 已实现基础链路 |
| 业务上下文连续 | 对象关联、刷新、返回及登录后回跳保持正确 | 已有结构改造与回归用例 |
| 统计可解释 | 指标说明数据范围、公式、时间及是否演示 | 部分实现，口径仍待统一 |
| AI 可配置且安全 | 管理员配置、业主隔离、失败可降级 | 基础能力已实现，依赖上游服务 |
| 具备发布条件 | 安全、备份恢复、性能、外部服务均通过验收 | 未完成，不宣称生产就绪 |

历史目标“效率提升 50%、满意度 90%、收缴率 95%、响应 2 小时”保留为业务候选目标，不作为已达成结果。正式使用前需确定统计周期、样本、责任人和基线。

### 2.4 范围与非目标

本版覆盖管理端九个业务域、业主端现有功能、双端共享数据、AI 配置、统计与发布要求。

以下不作为当前已交付范围：多小区租户隔离及跨平台互联、家属/租户/商户独立端、原生 App、微信小程序、真实微信/支付宝交易、电子发票、硬件实际开门、真实视频流、二手交易担保和物流、本地模型部署。

“社区公共帖子”指本平台普通业主共享的广场，不是多个独立社区系统之间的内容联邦。

## 3. 用户、身份与权限

### 3.1 用户模型

| 用户 | 当前身份/入口 | 允许范围 | 边界与缺口 |
| --- | --- | --- | --- |
| 系统管理员 | `userType=5`；`/login` | 管理业务、系统管理、AI 配置及快速重启 | 应进一步细化高风险权限与审计 |
| 物业管理类账号 | `userType=4`；`/login` | 当前粗粒度管理端业务 | 不等同于经理、客服、财务、维修员的细粒度隔离；AI 配置接口另限类型 5 |
| 普通业主 | 启用的 `userType=1`；`/community/login` | 本人业务、公开内容、本人发布、业主智能问答 | 禁止访问管理业务接口；不得伪装管理员 |
| 未绑定业主档案的普通账号 | 同普通业主入口 | 公开公告/活动/电话、社区互动、无私人上下文的智能问答 | 不得查看私人业务或提交房屋工单 |
| 家属、租户、商户、访客 | 当前主要为业务档案 | 由管理端维护相关记录 | 不宣称已有独立登录端及完整自助权限 |

未来业务岗位建议为系统管理员、物业经理、客服、维修、财务、安保，但岗位模型与数据范围属于后续权限工程，不应把现有角色管理页面视为全部落地。

### 3.3 身份与授权需求

| 编号 | 需求 | 现状 | 优先级 |
| --- | --- | --- | --- |
| AUTH-01 | 每次请求验证令牌，并重新确认数据库中的账号存在、启用及身份 | 已实现 | P0 |
| AUTH-02 | 业主只允许访问居民专用控制器和本人资料/密码/头像/退出等明确自助接口 | 已实现 | P0 |
| AUTH-03 | 私人数据归属以服务端身份计算，不信任客户端传入的业主 ID、用户 ID 或状态 | 业主接口已实现；管理写接口需继续专项检查 | P0 |
| AUTH-04 | 管理端实现菜单、按钮、接口与数据范围一致的细粒度授权 | 部分实现；不能仅依赖菜单显隐 | P0 |
| AUTH-05 | 账号与业主档案经有效关系绑定，绑定及解绑可追溯 | 读取链路已实现，完整绑定治理待完善 | P1 |
| AUTH-06 | 注册、短信、找回密码、登录限流达到真实身份验证和防滥用要求 | 有相关入口/实现，生产闭环待专项验证 | P0 |

账号 ID 与业主档案 ID 是不同对象：`sys_user.id -> base_owner.user_id -> base_owner.id`。不得直接以账号 ID 查询 `owner_id`。

业主房屋读取依据 `base_owner_house` 中 `relationType=1` 且起止日期有效的关系。管理端仍存在按房屋 `owner_id` 展示/筛选的旧链路，两者需统一；不能由“能打开房屋列表”推导出共有人和产权历史已经完整支持。

## 5. 业主端功能需求

### 5.1 首页与私人档案

| 编号 | 功能规则 | 状态 | 验收标准 |
| --- | --- | --- | --- |
| RES-01 | 展示关联房屋数、未缴清账单数、待处理报修数与公告快捷入口 | 已实现 | 计数仅属于当前业主；未绑定显示绑定提示，不伪装真实零业务 |
| RES-02 | 分页读取本人有效关系房屋，展示楼栋、单元、房号、面积 | 已实现 | 切换账号不残留上个账号的房屋 |
| RES-03 | 账单展示编号、收费项、房号、账期、应缴、已缴及状态 | 已实现，只读 | 不出现模拟扣款按钮，不允许读取他人账单 |
| RES-04 | 车辆展示本人车牌、品牌、颜色等现有字段 | 已实现，只读 | 不暴露全社区车辆或他人联系方式 |

当前私人列表接口单页大小上限为 50。新增筛选或导出时也必须保留服务端归属校验，不得以 URL 条件替代授权。

### 5.2 在线报修

需求 `RES-05`：普通业主可为本人有效关联房屋创建报修，查看处理进度与结果，并对本人已完成且未评价工单评分。当前已实现基础闭环，P1 继续完善附件、取消规则、指派和服务时限。

| 字段 | 当前规则 |
| --- | --- |
| 关联房屋 | 必填，只能选择本人有效房屋 |
| 标题 | 必填，最多 100 字 |
| 描述 | 必填，最多 2000 字 |
| 类型 | 必填，合法值 1 至 5，前后端标签保持一致 |
| 紧急程度 | 必填，1 一般、2 紧急、3 特急 |
| 联系人 | 必填，最多 50 字 |
| 联系电话 | 必填，符合当前大陆手机号校验 |
| 单号、业主、状态 | 后端生成或确定，不接受业主指定管理字段 |
| 评价 | 1 至 5 分；文字选填，最多 500 字 |

当前管理主链路：`0 待处理 -> 1 已派单 -> 2 处理中 -> 3 已完成`；取消状态为 `4`。评价记录评分与时间，不新增“已评价”工单状态。管理取消接口的合法前态仍需收紧，业主端当前没有自助取消入口。

验收：提交成功返回真实工单；管理端读取同一记录；派单、处理、完成后业主刷新能看到结果；未完成不能评价；非本人不能评价；重复评价和并发提交应专项验证，不因前端隐藏按钮而视为防护完整。

当前居民报修提交不包含照片上传字段，不将帖子/二手图片能力视为报修附件已经交付。

### 5.3 投诉建议

需求 `RES-06`：业主为本人房屋提交投诉或建议，查看状态、处理结果与物业回复。当前已实现创建和结果查询；评价、重开与申诉待建设。

标题、描述、类型、联系人及电话限制与报修公共字段一致，不包含报修紧急程度。当前状态为 `0 待处理、1 处理中、2 已完成、3 已关闭`；管理端支持受理、办结和完成后关闭，并保留待处理直接办结的兼容行为。未来应明确受理责任、回复必填与结案规则。

验收：客户端提交的业主、处理人、状态不能覆盖服务端值；物业回复与原投诉绑定；不向其他业主返回投诉内容；关闭/办结重复操作不得造成状态倒退。

### 5.4 公告、活动与电话

| 编号 | 需求 | 当前边界 | 后续方向 |
| --- | --- | --- | --- |
| RES-07 | 阅读社区公告 | 仅 `isPublish=1`、启用、发布时间已到；按置顶/发布时间展示 | 阅读记录、已读回执及消息送达待完善 |
| RES-08 | 浏览社区活动 | 只展示状态 1/2/3 的非草稿活动 | 业主报名、名额、取消、签到与评价待建设 |
| RES-09 | 查询便民电话 | 只展示启用记录、工作时间和地址 | 移动端拨号行为需按浏览器能力验收 |

活动是浏览能力，不因为管理端存在报名表或接口就宣称业主已经能报名。

### 5.5 个人中心

需求 `RES-10`：展示当前账号及普通业主身份；编辑姓名、手机号、邮箱、性别、生日；校验旧密码后修改密码。基础实现已具备。

当前业主页面展示已有头像，但没有与管理个人中心等同的头像上传交互，后续可补齐。个人资料编辑不能修改 `userType`、角色、启用状态、业主绑定或房屋归属；修改手机号不等于完成产权/身份重新认证；账号资料与业主档案的同步规则需明确。

### 6.3 图片与内容安全

需求 `SOC-04`：社区帖子和二手发布统一执行以下规则，当前基础实现已具备，存储治理待完善。

1. 每张图片不超过 2MB，只支持 JPG/PNG，边长不超过 4096 像素；服务端检查实际图片头和尺寸，而非只检查扩展名。
2. 每条记录最多 5 张，保存受限的本地资源地址；服务器生成随机文件名，拒绝任意外部地址和路径。
3. 用户文本与 AI 答案不直接作为 HTML 执行；不得通过图片或正文注入脚本。
4. 当前上传到本地 `uploads/community`；可访问地址不是私有附件授权方案，不应用于身份证、合同等私密文件。
5. 已上传但未引用文件当前保留。后续需清理策略、容量配额、引用检查、内容审核及备份恢复。

## 7. 智能服务需求

### 7.1 接入范围

需求 `AI-01`：管理员配置云端 OpenAI 兼容 API，无需绑定特定厂商，无需本地 Ollama。当前支持范围是兼容模型列表与聊天协议的服务，不是任意网址、任意鉴权方式或任意 API 自动适配。

| 配置项 | 行为与边界 |
| --- | --- |
| 启用开关 | 区分保存的启用状态与当前运行状态 |
| API 地址 | HTTPS 公网 Base URL；规范化为兼容 `/v1` 路径；拒绝本机及内网目标 |
| API Key | 后端保存，页面返回脱敏状态；留空时保留已有 Key，不代表删除 |
| 对话模型 | 从模型列表识别，并可按当前页面能力选择 |
| 向量模型 | 可选；无可用 embedding 模型时不应宣称知识检索已经启用 |
| 检测 | 当前主要调用 `/models`，检测成功不等于聊天、工具调用及向量调用全部成功 |
| 保存生效 | 写入运行配置文件；当前需重启后端后生效，不是无中断热更新 |

模型识别使用模型名称等启发式规则，不保证自动判定能力、计费和配额。供应商免费额度、余额、订单、区域、模型权限及网络均为外部依赖。

### 7.2 业主问答

需求 `AI-02`：业主以中文提问，系统异步提交、轮询结果、展示本人历史。当前已实现，不使用管理端全局工具，也不使用共享知识库检索。

| 授权数据 | 当前上下文范围 |
| --- | --- |
| 本人未缴清账单 | 总笔数与最近 20 笔，限当前业主 |
| 本人报修 | 总笔数与最近 10 笔，限当前业主 |
| 公告 | 最新 5 则已发布、启用且生效内容，单则正文做长度限制 |
| 活动 | 最新 5 项公开非草稿活动 |
| 便民电话 | 前 10 条启用记录 |
| 空闲车位 | 台账空闲总数和前 20 个位置；不是实时车位传感器数据 |
| 未绑定账号 | 不附带私人账单和报修 |

安全要求：只能回答授权资料；不查询其他住户；不修改账务、工单、门禁或配置；资料中的用户文字作为引用内容而非指令；过往活动不表述为即将开始；截取明细数不能冒充总数。模型输出存在错误可能，金额及状态以业务页面为准。

需求 `AI-03`：控制请求资源与任务归属。当前问题长度 1 至 2000 字；每账号最多一个未完成问题，相邻提交至少间隔 3 秒；执行器 2 个工作线程、等待队列 8；任务记录上限 200，已完成且超过 10 分钟的任务在新提交时清理。上述为当前实现参数，不是容量承诺。

接口：`POST /api/v1/resident/qa/questions` 返回任务 ID；`GET /questions/{id}` 返回 `pending/completed/failed`；`GET /history` 只返回本人业主问答历史。前端最长轮询约 180 秒；服务端运行任务在内存中，刷新不是恢复承诺，后端重启会丢失未完成任务。

成功且保存成功的问答历史在数据库中按账号隔离。历史保存失败不应丢弃已经得到的答案。上游失败或未配置时展示安全、可理解的提示，不把供应商原始报错、密钥或其他用户数据返回业主。

### 7.3 管理端问答与知识库

需求 `AI-04`：管理端可查询业务，并按配置使用知识库检索。当前已有 20 类查询工具，覆盖车位、账单、报修、投诉、公告、活动、快递、房屋、访客、通行、帖子、二手、投票、设备、报警、巡检、服务、电话、商品和租售。

这些工具属于管理范围，不能直接开放给业主。细粒度岗位权限落地时，工具查询也必须继承调用人的数据范围，而不是仅限制页面入口。

需求 `AI-05`：知识库维护、加载和检索状态真实可见。当前默认 `SimpleVectorStore` 为进程内存存储，重启后需要重新加载；没有持久化索引、高可用、全量文档解析正确性的交付承诺。答案引用来源、文档可见范围、删除后索引一致性及真实流式输出需专项完善。

### 7.4 后端快速重启

需求 `AI-06`：仅系统管理员可执行快速重启。当前实现依赖 Windows、JAR 运行方式和 `scripts/restart-backend.ps1`；IDE 运行、非 Windows 或脚本/JAR 缺失时必须明确拒绝，而不是提示成功。

重启需二次确认并阻止重复操作，提示短暂服务中断和未完成问答可能丢失；恢复后重新查询实际状态。当前按钮不等同于服务守护、零停机发布、自动回滚或跨操作系统部署管理。

### 7.5 AI 风险与合规

API Key 当前保存于后端本地运行配置文件，不是加密密钥托管。正式部署前必须限制文件 ACL、禁止进入 Git 与前端产物、对日志脱敏，并确定密钥轮换与删除策略。

业主提问及授权业务快照会发送给外部模型服务。正式启用前应告知用户数据用途、供应商及保留策略，评估个人信息合规和最小化传输。受限快照降低暴露范围，但不代表已经完成外部传输合规验收。

## 9. 跨模块共享与业务闭环

### 9.1 数据对象关系

```text
账号 sys_user
  -> 业主档案 base_owner（user_id）
     -> 有效产权关系 base_owner_house -> 房屋 -> 单元 -> 楼栋
     -> 本人账单 / 车辆 / 报修 / 投诉
  -> 本人帖子 / 评论 / 二手物品 / 问答历史（user_id）

业主端创建工单 -> 共用业务表 -> 管理端处理 -> 业主端读取同一记录
管理端发布公告/活动/电话 -> 可见性规则 -> 业主端与受限问答上下文
```

私人数据按业务对象归属隔离；公开内容也需要登录和可见性判断。“公共”不等于无需认证的互联网匿名访问。

### 9.2 当前对象跳转

| 来源 | 目标 | 关联条件 |
| --- | --- | --- |
| 楼栋/单元 | 单元/房屋 | `buildingId`、`unitId` |
| 业主 | 房屋、家属、账单、报修、访客 | `ownerId` 等实际接口条件 |
| 房屋 | 业主、账单、报修 | `id`、`houseId` |
| 账单 | 详情、缴费记录 | 账单 ID、`billId` |
| 缴费记录 | 原账单详情 | `billId` |
| 报修 | 工单详情、房屋账单 | 工单 ID、`houseId` |
| 设备/维保 | 设备详情/维保列表 | `equipmentId` |
| 便民服务 | 预约列表、新建预选 | `serviceId` |
| 访客 | 指定详情、关联业主 | 访客 ID、`ownerId` |

这些链接要求目标接口实际使用筛选条件；缺少关联 ID 不显示无效入口；非法站外返回地址不执行。详情直接打开应回到所属列表。列表筛选与访问授权是两项独立要求。

### 9.3 主流程与验收

| 流程 | 当前可用部分 | 必须满足的验收 |
| --- | --- | --- |
| 报修 | 业主创建、管理派单处理、完成、业主评价 | 两端同单号同状态；每个动作校验身份和合法前态 |
| 投诉 | 业主提交、管理受理/办结、业主查看 | 回复归属准确；他人不可读；不声称已有人点评价 |
| 财务 | 账单生成、模拟缴费、流水、退款冲减 | 原账单与流水可互查；模拟标识明显；失败不产生半笔账 |
| 装修押金 | 审批金额大于零时生成押金记录，有重复生成防护 | 重复审批不重复建单；生成、收取、退还分别可辨 |
| 访客通行 | 审批、选择设备核销、创建通行日志 | 详情 ID 正确、设备存在、同一访客关联准确；硬件另验 |
| 社区内容 | 业主发布、公共读取、管理隐藏或下架 | 隐藏后普通列表不可见，原作者不能自行绕过恢复 |
| AI 配置 | 检测模型、保存配置、重启、运行状态查询 | 保存值与运行值可辨；模型列表成功不冒充实际对话成功 |

## 10. 数据统计与图表

### 10.1 展示原则

需求 `DATA-01`：有业务统计价值的页面提供紧凑指标、趋势或结构图，帮助扫描和比较，不以装饰图代替有效信息。列表级统计应注明“当前页/当前筛选/全部数据”，不得混用。

需求 `DATA-02`：图表标注时间范围、单位、口径与更新时间；可回到明细核对；无数据、失败与示意数据分别展示。金额、笔数、比率不在同一未标单位的轴上直接比较。

### 10.2 当前统计成熟度

| 统计 | 当前实现 | 不能据此宣称的能力 |
| --- | --- | --- |
| 业主/房屋总数 | 业务表计数 | 不等于已认证入住人口 |
| 入住率 | `/report/owner` 使用房屋状态 1；大屏“occupiedHouses”使用 1/2/3 | 两者口径不一致，需统一后才能跨页比较 |
| 服务总数/完成率 | 报修、投诉计数；完成报修状态 3 | 取消是否进入分母需明确；不等于 SLA 达标率 |
| 年龄分布 | 当前接口为固定占位数据 | 不能称真实年龄画像；需接入合法生日数据或撤下 |
| 活跃度排名 | 当前接口返回空列表 | 尚无完整活跃度算法 |
| 平均响应时长 | 当前接口包含固定 2.5 小时和趋势文字 | 不是实测服务时长 |
| 财务概览/近月趋势 | 根据账单金额与状态聚合 | 应统一作废、退款、账期与现金流口径 |
| 在线摄像头/设备 | 根据台账状态计数 | 不是实时心跳探测 |
| 自定义报表 | 业主/服务/财务主题选择、指标图表、CSV、本地模板 | 不是任意拖拽分析、跨端同步模板或服务端报表引擎 |

当前自定义模板保存于浏览器 `localStorage`，不保证按账号隔离或跨浏览器同步，不应保存私人明细。后端模板保存接口存在空成功实现、列表为空；不得把它当作持久化模板能力。通用后端报表导出尚未开放，部分前端页面可导出 CSV；不能泛称全部支持 Excel/PDF。

### 10.3 建议统一指标口径

需求 `DATA-03`（P1）：以下作为后续统一口径，需产品/财务确认并落地，不视为当前接口已经全部遵循。

| 指标 | 目标定义 |
| --- | --- |
| 账期应收 | 指定账期内有效、未作废账单的应缴金额总和 |
| 账期净已缴 | 同一账单集合的有效入账减有效退款；模拟与真实资金分开展示 |
| 收缴率 | 账期净已缴 / 账期应收 × 100%；分母为零显示“无应收”，不误导为业务零收缴 |
| 欠费金额 | 同一有效账单集合中各笔 `max(应缴-净已缴, 0)` 之和 |
| 报修完成率 | 指定创建周期已完成单数 / 同周期有效单数；是否排除取消必须明示 |
| 平均首次响应时长 | 首次真实受理/派单时间减提交时间，未响应另计，不用处理完成时间代替 |
| 入住率 | 经业务确认的入住状态房屋 / 可统计房屋；租用、装修与入住分别定义 |
| 空闲车位数 | 有效车位台账中可分配的空闲状态数；不称实时物理空位 |

图表优先顺序：财务收缴趋势及欠费结构、报修数量/状态/响应趋势、房屋使用状态、车位状态、活动参与情况。活动参与图须等待报名数据闭环，年龄与活跃度图须等待真实可信数据。

## 11. 界面与交互要求

需求 `GEN-06`：管理端保持高效、清晰的业务界面，业主端突出高频服务与内容浏览。统一采用现有 Vue、Element Plus、公共表格/弹窗/表单与 ECharts，不另起一套视觉技术栈。

1. 页面层级为导航、标题/必要概览、筛选、主体、分页/操作；避免嵌套卡片和大面积装饰挤压业务数据。
2. 同类按钮、状态色、间距、日期和金额格式保持一致。状态不能只靠颜色表达。
3. 统计图与原列表、明细、审批、批量操作并存；不能因美化删除已有功能。
4. 新建、编辑和详情明确区分；只读字段不伪装可编辑；高风险操作二次确认。
5. 搜索无结果可清除条件；接口失败可重试；数据加载时不抖动；长文本和手机号不覆盖操作区。
6. 移动端优先保证业主高频功能，弹窗不超屏，输入框不遮挡提交；管理大表格可横向滚动，不承诺所有列强行压缩。
7. 图片有替代文字、占位与失败状态，点击可检查实物；示例素材保留显著标识。
8. 控件有明确标签、键盘焦点和可读错误提示；图表提供对应数值说明或表格。

需求 `GEN-07`：服务不可达与登录失效分开处理。前端地址拒绝连接说明前端服务未监听或不可达，不能用重新输入密码解决；后端不可达应提示服务错误，不应无依据清空当前会话并反复跳首页。

### 12.1 性能目标与验收口径

保留原 PRD 指标作为候选发布目标，不能写成现有测试成绩。测试前记录机器、数据量、网络、缓存、负载模型及观察时长。

| 候选目标 | 验收口径 |
| --- | --- |
| 1000 同时在线用户 | 在线会话数量不等于 1000 并发请求；应另定峰值 QPS 与操作分布 |
| 95% 页面主要内容可用时间不超过 2 秒 | 明确起点、首屏接口和静态资源是否冷缓存 |
| 普通 API P95 不超过 500ms | 排除外部模型、上传、复杂报表和大批量导出，分别建立指标 |
| 常规报表不超过 10 秒 | 明确时间跨度和数据规模 |
| 年可用性不低于 99.9% | 需监控、故障恢复与长期统计，本地运行不能证明 |

AI 当前队列较小，应单独测试供应商限流、排队、取消/超时和重启场景；不适用普通 API 500ms 的回答时延目标。

| AC-12 对象跳转 | GEN-04、ADM-06/13/21/26 | 房屋到账单到流水、设备到维保、服务到预约；刷新/返回保留对象 | `05-structure`、`06-live-structure`、后端结构测试 |
| AC-13 资金与库存 | ADM-15 至 ADM-20、NFR-02 | 模拟标签明确；重复回调/退款/审批与失败回滚不产生脏账或负库存 | 支付说明作为基线，需补高风险专项 |

## 16. 与历史 PRD 的主要变化

1. 从单一后台规划改为管理端与普通业主端双端产品，单独定义权限与共享数据。
2. 将 AI 纳入正式业务域，增加云端兼容 API、受限业主问答、异步任务与管理员重启约束。
3. 纳入已新增的二手图文、公共帖子、评论回复和示意素材规则。
4. 将“存在页面/表/接口”与“可用、闭环、生产就绪”分开，不沿用历史完成率。
5. 明确业主账单只读、活动只浏览、二手线下联系；不把规划能力写成当前交付。
6. 明确支付、监控、短信、在线设备和部分报表的模拟/占位边界。
7. 增加指标口径、跨模块关联、优先级、里程碑及可追踪验收用例。
