## 开发顺序

按“结构与入口 → 业务主体 → 联动与规则 → 细节和发布验收”推进。功能结构图中的数据库表不直接等同于独立页面，关联表由对应业务页面管理；每一步都要有真实入口、真实接口、正确对象关系和可复核的验收结果。

本轮交付的是第一批结构与互通改造，已经应用到本机正在运行的项目。它不代表全部 PRD 功能或全部跨模块业务已经完成。

## 已接通的对象关联

这些入口会携带业务 ID，目标页实际将该条件传给后端，不只是打开另一个列表。

| 来源 | 可进入的业务 | 目标条件 |
|---|---|---|
| 楼栋 | 单元、房屋 | buildingId |
| 单元 | 房屋 | unitId |
| 业主 | 当前归属房屋、家属、账单、报修、访客 | ownerId |
| 房屋 | 当前业主、账单、报修 | id / houseId |
| 账单 | 账单详情、该账单缴费记录 | 详情 ID / billId |
| 缴费记录 | 对应账单详情 | billId |
| 报修 | 工单详情、对应房屋账单 | 工单 ID / houseId |
| 设备 | 设备详情、维保记录 | 设备 ID / equipmentId |
| 维保记录 | 对应设备详情 | equipmentId |
| 便民服务 | 服务预约列表，新建时预选该服务 | serviceId |
| 访客 | 指定访客详情、关联业主 | 访客 ID / ownerId |

缺少关联 ID 的记录不会显示无效跳转。返回来源只接受能匹配业务路由的站内地址，直接打开详情或编辑页时使用其所属业务列表作为返回目标。

当前房屋列表按 house.owner_id 查询归属；共有人、历史归属和 owner_house 关联数据一致性要在房屋业主主体阶段统一。本轮没有新增房屋绑定写入口，以免把旧关系规则缺陷当作已解决。

访客详情现使用真实字段展示通行凭证，不再把随机字符串当作图片 URL。可扫描二维码生成、黑名单和有效期校验仍属于后续访客通行主体工作。

## 实际验证结果

- 原导航回归 12 项通过：未登录深链接、并发过期响应、旧令牌迟到响应、重复登录提交、安全返回地址、刷新和前进后退。
- 新结构与共享交互回归 14 项通过：九模块目录、房屋→账单→缴费、关联条件刷新/解除/返回、访客详情准确性、设备维保预选、服务预约预选、旧资料入口、菜单失败/空结果、无效操作按钮、同一组件切换对象、直接编辑提交返回，以及新旧弹窗数据提交。
- 真实后端浏览器检查 1 项通过：九模块菜单，全部可见入口的路由匹配，房屋→账单→刷新→返回，未捕获页面脚本错误。
- 后端单元测试 5 项通过：指定访客读取、无效设备禁止保存、负金额/空日期禁止保存、新建维保不得覆盖既有记录或跳过初始状态、不存在维保不能返回完成成功。
- 真实接口只读检查：一个选定房屋返回其 5 条账单；选定账单返回其 1 条缴费记录；指定访客 ID 正确；业主、服务项目和设备筛选生效。
- 菜单补丁连续执行两次，每个新增菜单仍仅一份。
- 前端标准生产构建、后端 package 均成功。本机后端已重启使用新包。

这些结果只证明上述范围。前端回归中的写请求由测试拦截，不会创建真实楼栋、电话或维保记录。真实环境检查只有登录和业务读取；数据库实际写入仅新增菜单及其管理员关联，没有重置、清空或重导业务数据。

## 后续主体工作顺序

### 第二批：基础档案、身份与操作基础

| 范围 | 需要完成 | 验收标准 |
|---|---|---|
| 账号、角色与部门 | 服务端角色/按钮/数据范围校验，用户与角色、角色与菜单配置的完整 UI，账号禁用失效与密码规则 | 普通业主不能读写管理数据或他人对象；配置修改能真实生效 |
| 业主与房屋 | 绑定入口、关系一致性、共有人及变更历史、实名核验、家属租户关系和到期权限 | 同一对象在房屋、业主、租户、账单页面身份和归属一致 |
| 车位车辆、装修 | 租购关系与收费依据，装修申请审批、押金收取状态、验收违规流程 | 业务状态有合法前后关系，不用一条普通编辑操作冒充审批或收款 |
| 结构图中的支撑模块 | 数据字典、系统配置、文件管理、消息中心、短信记录、通知公告的管理与业务调用 | 页面有真实数据来源，变更有校验与记录；不以空页面或固定成功提示表示完成 |
| 通用附件与日志 | 上传、保存、访问控制；关键操作日志写入、查询、导出 | 报修照片、头像等可以再次读取，关键修改能够追溯 |

这些属于主体能力，不应推迟到美化阶段。特别是已发现的权限、敏感信息和脚本注入问题，应在扩大居民可用范围前处理。

### 第三批：物业与财务主流程

| 主流程 | 后续重点 |
|---|---|
| 报修→派单→处理→确认→评价 | 自动/手动分派规则、人员选择、图片和进度、权限及结果一致性 |
| 投诉→受理→回复→评价 | 处理身份、状态限制、用户反馈 |
| 设备→维保→巡检→异常处置 | 维保时间联动设备台账、任务生成、巡检路线/GPS、故障联动工单 |
| 公告→定时发布→阅读→通知 | 真实阅读记录和通知送达，不只改发布标记 |
| 费用规则→账单→支付→缴费记录→退款→报表 | 收费范围、周期、一次性费用、交易去重、失败整体回滚、并发一致性、真实统计 |
| 装修/车位→押金→退款 | 明确实际收款与审批的区别，退款与账务同事务处理 |

订单失败仍扣库存、退款失败已改账、部分缴费回调重复入账等上一轮审查问题，本轮未声称修复。它们必须在相关主体流程验收前处理。

### 第四批：生活、互动、安防与 AI

| 模块 | 后续主体 |
|---|---|
| 商城与家政 | 购物车、价格服务端计算、库存事务、支付售后、服务人员派单与评价 |
| 房源与快递 | 房源审核/看房/合同/租金；取件码、核验、通知、滞留提醒 |
| 活动与互动 | 报名时间/名额并发、签到、照片评价；帖子评论入口、收藏举报；投票身份、选项和统计规则 |
| 安防门禁 | 访客有效期/黑名单/设备范围，可扫描二维码；真实门禁、监控和传感器接入 |
| AI | 工具身份隔离、消息安全渲染、知识索引真实重建、答案来源与问答记录、模型真实流式输出 |

AI 菜单可进入不等于模型已经启用；当前模型配置仍默认关闭。真实短信、微信/支付宝、硬件和模型调用需要各自的合法服务配置及验收，保留明确的演示/未接入状态。

### 第五批：细节与发布

在主体可用后统一处理：移动布局和浏览器兼容、空状态与加载状态、错误提示、字段名称、批量操作体验、慢查询、资源体积、监控告警、备份恢复及压力测试。

按 PRD 验收至少 1000 同时在线用户、普通 API ≤500ms、95% 页面 ≤2 秒、报表 ≤10 秒和年度可用性要求。本轮没有进行这些验收，也没有证明生产环境 HTTPS、备份和告警已具备。

## 后续开发约定

1. 每个新增菜单先确认真实路由、真实页面及所需角色；菜单查询失败不得恢复全部功能入口。
2. 每条关联按“来源对象 ID → URL 条件 → 后端筛选 → 结果归属 → 返回/刷新”验收；筛选条件不能代替服务端授权。
3. 新建/编辑沿用 ProTable、ProDialog、ProForm；遵守已修复的参数和提交契约。
4. 涉及金额、库存、权限、核销和审批的改动必须校验边界并包含相应测试。
5. 新增数据库变更使用增量脚本，保留现有业务数据；禁止为了演示重新导入全部测试数据。
6. 更新本清单时只记录已经实现并有证据的结果；延期项仍明确保留，不写笼统的“100% 完成”。
